AR-5RM Web Flasher

Backup, bootloader probe, and firmware flash for the Baofeng AR-5RM over a USB programming cable — straight from the browser, no scripts to run. Follows the tested radio_read.py → bootloader_probe.py → flash_bf.py sequence, in that order, enforced. Step 4 adds CPS settings & apps for a radio already running the custom bf-5rh firmware: that radio must be ON at its main screen (not flash mode, not stock firmware). Host note: macOS + the Prolific-clone cable does not work — use Windows Chrome/Edge.

STEP 0 Connect the cable not connected

Plug the programming cable into the radio's K-connector (push it in firmly — Baofeng jacks need a hard seat) and into this computer. Then click Connect and pick the cable's serial port from the browser's list. The port runs at 115200 8N1, no flow control for every operation. Nothing is sent to the radio until you start an operation below.
No port selected.

STEP 1 Backup — factory memory idle

Radio state: stock firmware, powered ON, sitting at its normal main screen. Follow CHIRP's order — it matters for this radio:
  1. Connect the cable first — seated hard in the radio and in this computer, and connected in Step 0 above.
  2. Then power-cycle the radio off → on with the cable already attached.
  3. Leave it a few seconds at the main screen before pressing Backup — a freshly booted radio with the cable already attached listens cleanly from power-up.
This reads the radio's full factory memory image (33,664 bytes) using the stock CPS protocol (PROGRAMBFNORMALU). It is read-only — the tool refuses to send anything except the handshake and read frames. No backup, no flash: the flash step stays locked until a backup completes in this session.

STEP 2 Probe — bootloader handshake idle

Put the radio in flash mode first:
  1. Radio OFF.
  2. Hold both small side buttons next to PTT (not PTT itself) and keep holding.
  3. Power ON. The screen stays black — that is flash mode. Release the buttons.
The probe only sends the bootloader handshake frame and listens — it cannot write anything. The flash step stays locked until the bootloader answers in this session.
Waiting. Up to 5 handshake attempts; the first attempt that hears anything decides.

STEP 3 Flash — write a .BF package locked

Radio state: still in flash mode (black screen, from Step 2). Choose a built-in firmware from the catalog, or upload the prepared .BF package file. The tool mirrors the tested flash_bf.py: single-region packages only, strict header checks, and a SHA-256 prefix gate before the Flash button can arm.
NRF dev unit only. Flashing is one-way off stock — there is no verified factory image to restore from. Unit 1 (BK) must stay stock and unflashed; never run this on it.

STEP 4 Radio settings & apps (CPS) locked

This step talks to a different radio state than Steps 1–3: the radio must be ON, running the custom bf-5rh firmware, sitting at its normal standby / main screen — not flash mode, not stock. It reuses the Step 0 port (115200 8N1). Nothing here auto-runs; every write below stays disabled until a CPS handshake succeeds in this page session.
bf-5rh dev unit only (the NRF unit). Unit 1 (BK) stays stock and must never be CPS'd — it would not answer this protocol anyway. Only connect Step 4 to the dev unit.
  • The radio scans for the CPS handshake at all times; on match its screen shows “CPS PROGRAMMING” and RF turns off.
  • 2-second idle timeout: if no CPS byte arrives for ~2 s the radio reboots out of the session on its own. This page refreshes the session automatically before an operation if it has gone stale, and keeps frames moving promptly during an operation.
  • The radio also reboots when the session ends — either via End CPS session below or ~2 s after the last CPS activity regardless.
  • Host note (same as Steps 1–3): macOS + the Prolific-clone cable does not work; use Windows Chrome/Edge.
Locked until the port is connected (Step 0) and the CPS handshake succeeds. Start with the radio ON at its main screen.

Set band lock

Changes only byte 29 of the settings record. The page re-reads the record fresh, writes it back with just that byte changed, then reads again — success is judged by the read-back, not the write ACK. (Why only byte 29 changes: the record is written back exactly as read, which is already the firmware's normalized form.)
Requires a successful CPS handshake and a settings read in this session, so the current value is known.

Install app (.app)

Choose a built-in app from the catalog, or upload a .app package. The page validates its 108-byte header in the browser before anything is sent — a build-hash mismatch means the app was built for a different firmware ABI and the radio would refuse to run it, so install stays disabled. Install erases the chosen slot, writes the file in 512-byte chunks, then reads the slot back and byte-compares it; success is claimed only on a matching read-back.
